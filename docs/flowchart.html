1. 全体像

層A（観察）は「回答と場面に何が書かれているか」を観察JSONにし、層B（受け手）は観察JSONを受け手の母集団 θ に通して所属度を出します。観察の作り方は4通り（LLM観察・代理観察・観察者の集団・System One）で、どれも同じ形の観察JSONになります。

6. 層A：観察者の集団（ensemble）

aggregate_sentences：plausibility は全観察者で平均（付けなかった観察者は 0）、severity は付けた観察者の最頻値、disclaimer は付けなかった観察者を none として票にする。aggregate_signals：intensity = 描写あり割合 × 強さの平均、virtual・congruent は多数決。

7. 層A：System One（s1.observe_turn）

1ターンを型付きの一段の質問（noul・score・choice）に分解し、1リクエストで問い、答えの確率をコードで観察JSONに組み立てます。数える・足す・上限で切る・重さを決める、はすべてコードです。

assemble：答えから観察JSONへ（s1:L413）

答えの読み出しは Answers（s1:L383）。yes() は noul ≥ 0.5（YES）、level()・top() は確率が最大の段階・選択肢。0.3〜0.7 の noul は unsure に記録（悪い読み・演技の読みは factual=False で記録しない）。

16. デバッグの勘所と要確認の箇所

図を書くためにコードを追った中で、経路によって振る舞いが変わる箇所と、意図を確かめたい箇所を挙げます。要確認は不具合の可能性があるもの、仕様は意図どおりと思われるが値を追うときに迷いやすいものです。

要確認System One 経路で但し書きの位置が「詫びより前」に倒れる
answer_disclaimers（L798）は a["sentences"] の中で詫びの語を含む最初の文を探し、それより前の但し書きを重く（×1.5）数えます。ところが s1.assemble（s1:L470〜478）は、悪い読みが 0.05 以上か但し書きのある文だけを sentences に入れます。詫びの文に悪い読みも但し書きもなければ sentences に入らず、first が None になって、すべての但し書きが「詫びより前」扱いになります。添字 i も元の文番号ではなく絞り込んだ後の番号です。LLM 観察（全文を記録する）では起きません。
要確認System One 経路では、最後の発話での約束の破りを数えない
build_state（s1:L161）は最後の user 発話を turns から外し、u{i}.repeat は turns の user 発話にだけ問います。そのため「直すと約束した直後のターンで、また同じ誤りを指摘された」場合（例の turn.json がまさにそう：a3.promise 0.9 の後に「二回伝えていますが」）、broken_promises は 0 のままです。prior_corrections は最後の発話を scar の current で補っていますが、broken_promises には対応する補いがありません。scar の 0.7·broken_promises、「破った約束の上に約束を重ねる」が効かなくなります。
要確認simulate・explain は観察を既定値とマージしない
cmd_scenes・cmd_fit・check_turn は merged(DEFAULT_*, …) を通しますが、cmd_simulate（L1047）と cmd_explain（L1232）は観察JSONをそのまま渡します。judge_full は a["apology"]["thanks_instead"] などを添字で読むので、LLM の観察で欄が欠けると KeyError になります。数の欄の "unknown" も coerce されずに演算に入ります。同じ観察でも simulate と fit で値が変わりうる点にも注意が要ります。
要確認出どころの較正を呼ぶコマンドが限られる
use_source は simulate・fit・explain だけが呼びます。scenes と check は既定の所属度関数のままです（現状 system-one の較正はないので check の結果は変わりません）。また configure は呼ばれるたびに、その時点の JUDGMENT を JUDGMENT_BASE にするため、同じプロセスで use_source("llm…") の後に load_population を呼ぶと（例：hook から check_turn を繰り返す、評価スクリプトから複数回読む）、llm の較正が基準に焼き込まれます。
要確認replay はハッシュを照合しない
ask（s1:L367）の replay は質問の組が変わっても保存済みの答えをそのまま読みます。質問 ID が変わった場合、欠けた答えは Answers の既定値（noul 0・段階 0・既定の選択肢）になり、エラーにならずに値だけが変わります。質問を変えた後は --cache で取り直すか、--debug の _raw.questions と答えの ID を突き合わせてください。
仕様L は回答に依存しない
perceive は場面と θ だけを見ます。同じ会話の回答は良くても悪くても同じ L（例では 3.9）になります。回答の差は judge_full の失点・不足・過剰にだけ現れます。
仕様失礼の所属度には下限がある
offense = 0 でも σ((0 − 1.2)/0.3) = 0.018。check の羊は 0.15 からなので鳴きませんが、平均所属度を比べるときは 0 ではなく 0.018 が基準です（較正後の llm では σ(−8) ≈ 0.0003）。
仕様verdict と羊の基準が違う
verdict の rude は tail.rude（所属度 0.5 以上の人の割合 ≥ 0.2）、羊は mu.rude（平均）です。「verdict は rude なのに羊が小さい」「warn なのに羊が鳴かない（light が原因）」は起こりえます。
仕様distance_shift の数え方が経路で違う
proxy（L338）は丁寧語の文末の比率の上昇を正規表現で数え、System One（s1:L420）は丁寧語への切替と呼び方の変化をモデルに問います。同じ会話でも 0〜3 の値がずれることがあり、L の detect·distance_shift の項に直接効きます。
仕様場面は sid で一意
観察JSONの scenarios は sid をキーにします。複数の run が同じ sid を持つと、observe（L152 の再開判定）・proxy（L422）とも最後の run の場面で上書きされます。run ごとに場面の会話が違う場合は値が混ざります。
仕様text_len の数え方が経路で違う
simulate・scenes は回答本文全体の文字数（成果物を含む）、check は own_part の後の文字数（成果物を除く）を「長さ」の失点に使います。
