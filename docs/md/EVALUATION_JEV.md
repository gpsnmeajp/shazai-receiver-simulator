# Jev 評価（層Aの System One 経路、2026-11-19）

[JEV_DESIGN.md](JEV_DESIGN.md) の7章の検証を、**実際の Jev** で行った記録です。Jev は OpenRouter の Decisions API で呼びました（`~typesafe/jev-latest`。実際に答えた版は `typesafe/jev-1.14-20261014`）。Jev 以外の LLM の役割（一括の観察、同じ質問の組に答える互換の判定器）は、**Claude のサブエージェントで代替**しました。データは `eval/jev/` にあります。

## 1. 要点

1. **Jev は、層Aの System One 経路の質問の組に、速く安く答えます。** 1回答あたり約100〜210問を、中央値 約340ms で返しました。ベンチマーク192回答（39,510問）は 約0.19ドル、項目の組106回答（21,323問）は 約0.08ドルです。型の誤り・欠けた答えは 0 件でした。
2. **事実型の欄は正確です。** 詫びの有無・軽口・許しの当然視は、項目の組の手の観察に対して AUC 1.00 でした。較正された構えは 0.94 です。
3. **規範的な区別の欄は、真の側へ大きく寄ります。** 詫びの文124のうち123を「許しを求める文」と答え、過失を認める文（「見落としていました」）を「弁解」と答え、謝ってその場で直す回答をすべて「先を急ぐ」と答えました。悪い読みの確率は 0.14〜0.53 に広く散らばります。9つの型の最大を取るため、項目の組の88%の回答で、どれかの文が 0.5 を超えました。
4. **そのまま層Bに通すと、ほぼすべての回答が「失礼」になります。** 項目の組の失礼の平均所属度は 0.97 でした（手の観察では 0.18）。手の観察を通した結果との κ は 0.01 です。
5. **ただし、確率の順位には情報があります。** ベンチマークでは、弁解・先を急ぐ・提案・約束・相手への指摘の AUC は 0.82〜0.95 でした（銀ラベルは観察者の集団）。ずれているのは閾値です（最適な閾値は 0.5 ではなく 0.88〜0.92）。ベンチマークで欄ごとの閾値を当てはめ（設計の5.6節）、それを項目の組に当てると、κ は 0.24、仮説の効果の検出は 11/13 まで上がりました。後者は一括の観察（サブエージェント）と同じです。
6. **差の原因を、質問の分解とモデルに切り分けました。** 項目の組の日程53回答で、手の観察を通した結果との κ を比べました。一括の観察（サブエージェント）は 0.70、同じ分解した質問の組にサブエージェントが答えると 0.50、Jev（較正つき）は 0.11 でした。分解とコードでの組み立てで約0.2、モデルの違いでさらに約0.4 落ちています。
7. **Jev に直接評定させる方式（P1 を破る方式）は、「失礼」をほとんど選びません。** ベンチマークで、観察者の集団が失礼とした30回答のうち、Jev が失礼を選んだのは 0 件でした（κ −0.03）。項目の組の「近さ」が 0.857 と高く見えたのは、「常に釣り合う」（0.806）と同じ仕組みで得をしたためです（[HISTORY.md](../../HISTORY.md) 3.4節）。
8. **前処理の不具合が2つ見つかり、修正しました**（4.4節）。どちらも Jev ではなく `s1.py` の正規表現の問題で、括弧書きを顔文字・ト書きと数える不具合と、「」の中の「？」で文を切る不具合です。
9. **採否（設計7章の基準）：** 段階1は、事実型の欄は基準を満たしますが、規範的な区別の欄と悪い読みは満たしません。段階2（筆者の評定との κ）と段階3（人間のブラインド評定）は、筆者の評定（`runs/`）が手元にないため実施していません。**現時点では、Jev を層Aの既定にはしません。** 組み込み判定（`check`）では、較正の表をつけて使う「試験的な選択肢」にとどめます。

## 2. 方法

| 役割 | 担い手 | 規模 |
|---|---|---|
| System One 経路の判定器 | **Jev**（OpenRouter Decisions API、`~typesafe/jev-latest` → `typesafe/jev-1.14-20261014`） | ベンチマーク192回答・項目の組106回答。1回答1リクエスト。2回ずつ問い、再現性も測った |
| Jev 直接評定（比較用） | Jev。4値の Choice（選択肢の順序を逆にした2回の平均）と述語ごとの Noul | 同上 |
| 一括の観察（`observe_prompt.md`） | 既存のサブエージェントの観察（v0.9 の観察者の集団6変種と、項目の組の盲検の観察） | 既存のデータを再利用 |
| 同じ質問の組に答える互換の判定器（`llm-s1`） | **サブエージェント6体（新規）**。盲検。問いごとに独立に確率で答える | 項目の組の日程53回答・9,038問 |
| 正解（金ラベル） | 項目の組の手の観察（`examples/scenes-kit.json`）と、それを母集団に通した予測 | 106回答 |
| 銀ラベル | 観察者の集団（6変種の集約、`eval/observers/obs-ensemble.json`） | ベンチマーク192回答 |

- Jev には、項目の組とベンチマークの、観察者に渡したのと同じ資料（`eval/observers/batches/`）を送りました。公開データだけで、人間の評定は送っていません。
- 受け手は500名（項目の組の比較は300名）、乱数の種は7です。
- Jev の観察は「出どころ system-one」として通しました。所属度関数の較正（`judgment_by_source`）はありません。サブエージェントの観察は、既存の較正（`llm`、`llm-ensemble`）で通しています。この差は Jev に不利に働きます。
- **筆者の評定を使う比較（段階2）は、していません。** ベンチマークの実行先（SHAZAI Rules リポジトリの `runs/`）が、この環境にはないためです。ベンチマークでの比較は、観察者どうしの比較にとどまります。

### 4.7 組み込み判定（`check`）の作例

| 作例 | 手の答え（replay） | Jev（較正なし） | Jev（前処理修正・較正つき） |
|---|---|---|---|
| 弁解・相手への指摘・先送りを含む回答 | 失礼の恐れ メッ！！（失礼 1.00） | 失礼の恐れ メッ！！（1.00） | 失礼の恐れ メッ！！（1.00） |
| 過失と負担を具体的に述べ、その場で直した回答 | 問題なし（失礼 0.02、釣り合う 0.73） | 失礼の恐れ メッ！！（1.00） | 問題なし（失礼 0.11〜0.22。5回中4回「メ…？」） |

Jev の答えは毎回少し違うので、Jev の列は同じ入力で3〜5回ずつ実行しました。悪い回答は、どの設定でも毎回捕まえます。良い回答は、較正なしでは毎回「失礼の恐れ」になり、較正つきでは毎回「問題なし」になりました。ただし、項目の組全体では較正後も「失礼」の誤報が多く（4.5節・4.6節）、二つの作例だけで判断はできません。差し戻し（`SHAZAI_MODE=block`）に使うには、まだ早い状態です。

## 5. 考察

### 5.1 「細部に過敏で、全体に寛容」という Jev の二面性

同じモデルが、正反対の方向に外れました。層Aの一段の問いでは、どの文にも悪い読みの余地を認め、詫びを許しの要求と読み、過失の告白を弁解と読みます。ところが回答全体を直接問うと、失礼をほとんど選びません。

これは、二つの読み方の違いとして理解できます。一段の問いは「この文を X と受け取る**余地はあるか**」という可能性の問いです。字義通りに読むモデルにとって、ほぼすべての日本語の詫びには、何らかの余地があります。「申し訳ありません」は、語源をたどれば「言い訳のしようがない」で、許しを乞う構造を確かに含みます。「見落としていました」は、確かに失敗の事情の説明です。Jev は間違っていません。区別が**規範的**だから外れたのです。「弁解」と「過失の告白」を分けるのは、文の意味ではなく、その文が責任をどこに置くかという働きです。

一方、直接の問いは「全体としてどれか」という**典型の問い**です。AIアシスタントの回答の多くは丁寧で、典型的には「釣り合う」に見えます。ペルソナ評定が失敗した理由もここにありました。人間が失礼と感じるのは典型からの小さなずれで、ずれの位置（詫びの前の但し書き、H8b・H8c）を直接評定はほとんど拾えませんでした（+0.02、−0.00）。

層Bは、この二つを橋渡しするために作られています。細部の確率を、受け手の多様さを通して全体の分布に積み上げます。今回の結果は、その橋が**入力の確率の較正に強く依存する**ことを示しました。一つひとつは小さな過敏さ（0.3 の余地）でも、9つの型の最大を取り、文の数だけ足すと、確実な失点に積み上がります。観察の揺らぎが、層Bで増幅されるのです。

### 5.2 確率の意味：「余地」と「頻度」

設計の5.4節は、Jev の確率が「読み手の分かれ方」を表すのか、「モデルの迷い」を表すのか、公開資料からは分からないとしていました。今回の結果は、第三の解釈を示しています。Jev の悪い読みの確率は、どちらでもなく、**「その読みが論理的に成り立つ度合い」**に近いようです。「苛立った受け手にとって自然か」と問うても、苛立ちの強さに応じて読みを絞ることはしません。

層Bの式 `p^(1/partisanship)` は、p を「苛立った受け手がそう読む頻度」として使います。余地と頻度は単調な関係にありそうですが、同じ尺度ではありません。今回の閾値による再較正（logit のずらし）は、その写像の最も粗い近似です。人の評定で、悪い読みの頻度そのもの（10人中何人がそう読むか）を集めれば、この写像を直接当てはめられます。人間の評価キットに、一文ごとの「そう聞こえるか」の問いを足す価値があります。

### 5.3 分解の代償と、分解の利点

同じ判定者（サブエージェント）で、一括の観察から分解した質問に替えると、κ は 0.70 から 0.50 に落ちました。分解には代償があります。一括の観察では、観察者は回答全体を読んだうえで「この文は弁解か」を決めます。分解した問いは、設計どおり互いに独立です。文脈から切り離された問いは、規範的な区別をしにくくなります。

ただし、分解には、一括の観察にない利点もあります。

- **欄ごとに直せる。** 今回、「許しを求める」「弁解」「先を急ぐ」のずれを、欄ごとに特定して閾値を直せました。一括の観察では、どの判断がずれたかを外から特定するのは難しいです。
- **安い。** 一巡0.2ドル以下なので、問いの書き方を変えた版を何度でも試せます。
- **同じ問いで、別のモデルを比べられる。** 今回の「モデルの違いか、分解か」の切り分けは、分解した質問の組があったからできました。

5.1節の分析からは、次の改善の方向が見えます。規範的な区別の問いに、**対比の基準を書く**ことです。たとえば「弁解」に「自分の過失を認める文（〜を見落としていました）は弁解ではない。弁解は、原因を自分以外に置くか、過失を小さく見せる文」と書きます。「許しを求める」には「詫びの言葉だけでは許しを求めているとみなさない。『お許しください』のように言葉で求める文」と書きます。Jev の資料は、領域の知識を criteria に書くよう勧めています。今回は閾値で吸収しましたが、問いの側で直すほうが、版を上げたときに強いはずです。

### 5.4 距離の変化：日本語の察しの難所

Jev が見落とした数少ない欄が、ユーザーが丁寧語に切り替えたこと（0.37 対 0.88）でした。これは本シミュレータで最も日本語らしい信号です。くだけた口調のユーザーが「そうですね。考えておきます。」と返すとき、言葉は丁寧でも、距離は開いています。Jev の弱点の「間接性」がここに出ています。

この欄は、半分はすでにコードで測っています（絵文字の消失、文量の減少、相槌化）。丁寧語の比率（`polite_ratio`）もコードで測れるので、モデルに問わずに済む部分を増やせます。System One に問うのは、コードで測れない残り（呼び方の変化など）だけにする。設計の原則「モデルには一段の判断だけを問う」を、さらに一歩進める方向です。

### 5.5 組み込み判定の使い道

速さと安さは本物でした（1ターン 0.3〜0.7秒、約0.001ドル）。ただ、良い謝罪にも「メッ」と鳴く羊は、肩に乗せられません。現状の精度で意味のある使い方は、次のようなものです。

- **悪い回答の網として使う。** 悪い回答の作例は、どの設定でも確実に捕まえました。ベンチマークでも、集団が失礼とした30件の取りこぼしは 0 です。誤報は多いですが、取りこぼしが少ない検査は、二段の検査の一段目になります。Jev で「失礼の恐れ」とされたものだけを LLM（一括の観察）に回せば、費用の大半を Jev の価格で済ませられます。
- **一文の寄与を測る（設計8章）。** 誤報の原因の多くは、特定の文の悪い読みでした。文を一つずつ抜いた版を観察すれば、どの文がどれだけ失点を作ったかを示せます。誤報であっても、「この文は、こう読まれる余地がある」という指摘は、書き手にとって意味のある情報です。羊の「メ…？」は、叱責ではなく問いかけとして使えます。

### 5.6 この評価の限界

- **人間の評定との比較をしていません。** 基準は、手の観察（項目の組の設計者による）と、それを母集団に通した予測、および Claude の観察者の集団です。シミュレータの理論に照らした一致であって、人間の受け止め方との一致ではありません。
- 項目の組は設計された項目で、手の観察の正例が 0 の欄が多くあります（弁解、許しを求める、悪い読みなど）。AUC はそれらの欄で出せません。
- 較正の表は、ベンチマークの銀ラベル（Claude の観察）に合わせたものです。Jev を Claude の観察に近づけただけで、真の値に近づけたとは限りません。
- 互換の判定器も、比較の基準の一つ（一括の観察）も、Claude です。サブエージェントのうち2体は、同じ文に同じ判断を使い回したと報告しています。1体は、自分の担当外のファイルの行数を一覧で見てしまったと報告しています（中身は開いていない）。

## 6. 次の手順

1. **筆者の評定での段階2。** SHAZAI Rules リポジトリの `runs/` を置き、`tools/evaluate.py runs/* --obs jev=eval/jev/obs-bench-jev-pp-cal.json …` を実行します。Jev の観察は、この評価のために `eval/jev/` に保存してあります。
2. **問いの側の修正**（5.3節）。弁解・許しを求める・先を急ぐ・悪い読みに対比の基準を書いた版を作り、閾値なしでどこまで戻るかを測ります。
3. **履歴への問いの見直し**（4.5節）。過去のAIの発話の詫び・約束は、事実型の欄です。Jev が項目の組で過剰に検出する原因を、文単位で調べます。
4. **丁寧語の切り替えをコードで測る**（5.4節）。
5. 人間の評価キットに、一文ごとの「そう聞こえるか」の頻度の問いを足すかを検討します（5.2節）。

## 7. データと再現

`eval/jev/` に置きました。Jev の生の答えはキャッシュ（`cache/`、`cache-run1/`）にあるので、API なしで再集計できます。

| ファイル | 内容 |
|---|---|
| `cache/` | 2回目の Jev の答え（選択肢の順序を区別する鍵）。前処理の修正後の答えも含む |
| `cache-run1/` | 1回目の Jev の答え（旧い鍵 `request_hash_v1`）。再現性の比較用 |
| `obs-{bench,scenes}-jev.json` | 較正なし・前処理修正前 |
| `obs-{bench,scenes}-jev-cal.json` | 較正つき・前処理修正前 |
| `obs-{bench,scenes}-jev-pp-cal.json` | 前処理修正・較正つき（**最終**）。`-pp.json` は較正なし |
| `jev_calibration.json` | 欄ごとの閾値（`--calibration` で読む） |
| `direct-{bench,scenes}.json` | Jev 直接評定 |
| `llm-s1-subagent/`、`obs-scenes-s1sub.json` | 同じ質問の組にサブエージェントが答えたもの（日程53回答、前処理修正前の質問） |
| `calibration.md`、`fields-scenes.md`、`stability.md`、`direct-scenes.md`、`direct-scenes-schedule.md`、`bench-compare.md`、`scenes-obs-*.md` | 各表 |

```text
# Jev で観察（OPENROUTER_API_KEY。キャッシュがあれば問い合わせない）
python3 tools/observe_s1_batches.py eval/observers/batches/scenes-*.json --cache eval/jev/cache -o eval/jev/obs-scenes-jev-pp.json
# 欄ごとの閾値（ベンチマーク × 観察者の集団）
python3 tools/calibrate_s1.py eval/observers/batches/bench-*.json --cache eval/jev/cache -o eval/jev/jev_calibration.json --report eval/jev/calibration.md
python3 tools/observe_s1_batches.py eval/observers/batches/scenes-*.json --cache eval/jev/cache --calibration eval/jev/jev_calibration.json -o eval/jev/obs-scenes-jev-pp-cal.json
# 直接評定・比較・安定性
python3 tools/jev_direct.py eval/observers/batches/scenes-*.json --cache eval/jev/cache -o eval/jev/direct-scenes.json
python3 tools/eval_jev_direct.py --direct eval/jev/direct-scenes.json --obs jev-pp-cal=eval/jev/obs-scenes-jev-pp-cal.json --obs sub=eval/observers/obs-scenes-opus.json -o eval/jev/direct-scenes.md
python3 tools/compare_bench_sources.py ensemble=eval/observers/obs-ensemble.json jev-pp-cal=eval/jev/obs-bench-jev-pp-cal.json --direct eval/jev/direct-bench.json -o eval/jev/bench-compare.md
python3 tools/jev_stability.py --old-cache eval/jev/cache-run1 --cache eval/jev/cache -o eval/jev/stability.md  # stability.md は前処理の修正前の質問の組で作った。修正後のコードでは、問いが変わった回答が比較から外れる
# 組み込み判定
python3 sim.py check examples/check/turn-good.json --backend jev-or --calibration eval/jev/jev_calibration.json
```

注意：`obs-*-jev.json` と `obs-*-jev-cal.json`、`obs-scenes-s1sub.json` は前処理の修正前の質問の組で作りました。修正後のコードで同じコマンドを実行すると、`-pp` の版と同じものになります。
