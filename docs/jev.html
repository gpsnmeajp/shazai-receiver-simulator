層Aを System One モデル（Jev）に置き換える

層A（観察）の LLM を、TypeSafe AI の System One モデル Jev、または同じ API を話す互換バックエンドに置き換えられるかを検討し、その設計をまとめた文書です。層B（受け手モデル）は変えません。

状態：設計。組み込み判定モード（sim.py check、5.8節）だけ実装済み。Jev の実際の応答では未検証です。2026-11-18 時点の一次資料に基づきます。作成した環境からは TypeSafe の API に接続できなかったため、Jev が日本語で実際にどう動くかは確認していません。

1. 結論

置き換えは可能

層Aは、もともと System One 向きの形をしています。observe_prompt.md は「判断せずに、決まった欄に、決まった値域で記録する」指示で、欄の大半は真偽・0〜2 の段階・列挙値です。これは Jev の Noul（真偽の確率）・Score（順序のある段階）・Choice（列挙）にそのまま対応します。

そのまま移せないのは3種類

(1) 生成（依頼の抜き出し、悪い読みの文章、シグナルの列挙）、(2) 数えること（指摘・詫びの回数）、(3) 文の分割。「コードで候補を作り、Jev には候補ごとに判断させ、数はコードで足す」形に組み直します。

一番効くのは「一文の悪い読み」

層Bは悪い読みの文章を使わず、plausibility と severity だけを使います。言葉で書かせた確率は較正が悪いことが知られていますが、Jev は確率そのものを返し、較正を目的に訓練されています。層Bの式 p^(1/partisanship) が求めているのは、まさにこの確率です。

一番の危険は「字義通りに読む」性質

皮肉・慇懃な指摘・距離の変化は、言外の意味の読み取りです。悪い読みを「責任転嫁に聞こえる」などの具体的な型に分け、例を添えた一段の問いにして避けます。日本語での性能は未確認なので、採否は検証で決めます。

互換バックエンドを同じ形で持つ

TypeSafe 自身が、同じ質問を LLM に答えさせる互換アダプタ（system-one-adapter）を公開しています。本設計でも質問の組を一つにして、Jev と LLM の両方で同じ質問を実行し、欄ごとに比べられるようにします。

設計原則 P1（観察と評価を分ける）は、より強くなります。現行では、LLM が観察の中で「量」「回数」「強さ」もまとめて決めていました。新しい形では、モデルが答えるのは一文・一発話についての一段の判断だけで、数える・合成する・重さを決める部分はすべてコードに移ります。

5. 設計の詳細

5.1 リクエストの単位

Jev では、一つのリクエストの質問がすべて同じ state を見ます。無関係な情報が多い state では精度が落ちるので、ベンチマーク用には state を三つに分けます（組み込み判定では1リクエストにまとめます。5.8節）。

単位state質問数の目安
場面前半のユーザー発話、最後のユーザー発話、発話の配列距離の変化、不満の明示、損害、違反の種類、枠組み、発話ごとの指摘・押し付け・詫び・約束20〜60
依頼の抜き出し最後のユーザー発話の文の配列文ごとの依頼・質問の判定文の数×2
回答状況、依頼の配列、回答（自分の発言の文と成果物）回答全体の問い、文ごとの問い、悪い読みの型、依頼ごとの遂行、シグナル150〜250
  • 回答ごとに独立したリクエストにします。現行の observe は同じ場面の回答をまとめて送るので、指示で禁じていても回答どうしの比較が入りえます。Jev ではこの混入が構造的に起きません。
  • 追加の質問の費用は小さいので、「投機的に全部問い、使う答えをコードで選ぶ」（Speculative fan-out）形をとります。
  • 文を指すときは answer.own_sentences[3] のように state の中の位置を名指しし、間接性を減らします。

5.2 前処理でコードが受け持つもの

文の分割

。！？!? と改行で分ける

成果物の切り出し

コードブロック、件名、--- 以降。下書きの中の詫びを、ユーザーへの詫びと数えないため

絵文字・感嘆・顔文字、書式、丁寧語の比率、文字数、文量の比。モデルの弱点が「数」で、正規表現で正確に取れるため

候補の絞り込み

詫びの正規表現などは、どの文に詳しい問いを向けるかの目安にだけ使い、判定は Noul に任せる

5.3 一文の悪い読みの再設計

現行では、LLM が文ごとに悪い読みを文章で書き、自然さ（plausibility）と重さ（severity）を数字で付けています。これを型ごとの一段の判断に分けます。各型は Noul で、真・偽の側にそれぞれ日本語の例を付け、「単語だけをこじつけた読みは偽」を偽の側の定義に入れます。

型苛立っている相手がこの文を読んだとき、次のように受け取るのは自然かseverity
他人事自分の過失を他人事のように語っている1
言い訳責任を逃れるための言い訳をしている1
責任転嫁相手や状況に責任を押しつけている2
押し付け頼んでいない考えや作業を押しつけている1
恩着せ何かをしてやったと恩に着せている2
突き放し相手を突き放している、会話を打ち切ろうとしている1
軽さ事態を軽く扱っている1
逆ギレ謝る側が逆に不満を向けている2
慇懃丁寧な言葉の裏で見下している、皮肉を言っている2
  • 文の plausibility はコードで合成します。既定は max（最も自然な読み）で、比較用に noisy-OR 1 − Π(1 − p_k) も出します。severity は max を与えた型の表の値です。
  • 重さの判断が観察から抜けてコードに移るので、P1 とも P9（規則を根拠に対応づける）とも整合します。型と重さの表の根拠は 根拠 に書きます。

5.4 確率の受け渡し：観察の揺らぎと受け手の揺らぎ

Jev は点ではなく分布を返します。観察JSONは現行と同じ形の点の値を持ち、別に確率の付録 _p を持ちます。層Bには --obs-mode を足します。

モード点の値の作り方意味
point（既定）真偽は p ≥ 0.5、Score・Choice は最大確率の段階現行と同じ入力。P10（互換性）を守る
expected真偽は p、Score は期待値閾値の判定は丸める
sample受け手ごとに分布から引く観察の不確かさを、受け手ごとの読みの違いとして流す

事実型

詫びがあるか、冒頭か、依頼を果たしたか、絵文字の量など。揺らぎはモデルの誤りで、受け手の違いではありません。point で使い、確率が 0.3〜0.7 のものは「要確認」として記録します。

解釈型

悪い読みの自然さ、演技に見えるか、過失が曖昧か、距離の変化、皮肉の有無。揺らぎの一部は、受け手ごとに読みが分かれることの反映でありえます。sample で流す候補です。

設計原則 P11「確率とファジィを混ぜない」と同じ問題です。解釈型の揺らぎを受け手の揺らぎとして流すと、層Bがすでに持つ受け手の多様さ（partisanship など）と二重に数えるおそれがあります。Jev の確率が「読み手の分かれ方」なのか「モデルの迷い」なのかは、何に対して較正されたかに依存し、公開資料からは分かりません。決まるまでは、plausibility と performative_plausibility だけを確率のまま使います（現行もそうしているので、新たな二重計上は生じません）。

バックエンド中身用途

5.6 較正

  1. 金ラベルを作る50〜100回答について、人が観察JSONの正解を付けます。既存の LLM 観察は銀ラベルとして使えます。
  2. 欄ごとに較正を見るJev の確率と金ラベルの信頼性図と Brier スコアを出します。
  3. 再較正するずれる欄には、欄ごとの単調な再較正（等張回帰）をコードでかけます。閾値は 0.5 に固定せず、欄ごとに決めます。
  4. 版ごとに保存する再較正の表は jev_calibration.json に版ごとに保存し、版を上げたら作り直します。

5.8 組み込み判定モード（実装済み・オプション）

hook などでAIの応答を毎ターン判定する仕組みの参考として、1ターンを判定する check コマンドと、ほかのプログラムから呼べる関数 sim.check_turn があります。層Aを System One で観察し、そのまま層Bの母集団に通します。ほかのコマンドとは独立しています。

python3 sim.py check examples/check/turn.json                      # Jev（TYPESAFE_API_KEY）
python3 sim.py check turn.json --backend llm-s1                    # 互換モード（OPENROUTER_API_KEY）
python3 sim.py check turn.json --backend replay --replay answers.json   # 保存した答えで再現
cat turn.json | python3 sim.py check - --json --fail-on rude       # 標準入力、JSON出力、失礼なら終了コード2

入力は {"messages": [{"role": "user"|"assistant", "content": "…"}, …], "answer": "判定する応答"} です。answer を省くと最後のAIの発話を判定し、context を渡すと場面の枠組みを上書きします。

母集団（既定300人）に通し、受け手ごとの所属度を集計して、次の三つに判定します。

rude（失礼の恐れ）

失礼と感じる人（失礼の所属度0.5以上の人）の割合が --rude-at（既定 0.2）以上

warn（要注意）

失礼か足りないの平均所属度が --warn-at（既定 0.4）以上

ok（問題なし）

どちらにも当たらない

作例での結果（仕組みの試験）

同じ会話（UTC で保存するよう二回頼んだのに直っていない場面）に対する二つの応答。答えは仕組みの試験のために手で付けた確率で、Jev の応答ではありません（examples/check/）。数値は平均所属度で、述語は排他的ではないので和は1になりません。

Stop hook の参考実装

examples/hooks/shazai_stop_hook.py は、Claude Code の Stop hook として、会話の記録（transcript）から最後のユーザー発話とAIの応答を取り出して判定します。ツールの結果は発話に数えず、続けて出たAIの文章は一つの応答にまとめます。

{"hooks": {"Stop": [{"hooks": [{"type": "command",
    "command": "python3 /path/to/shazai-receiver-simulator/examples/hooks/shazai_stop_hook.py"}]}]}}
環境変数働き
SHAZAI_MODEnotify（既定）：判定をユーザーに表示するだけ。block：「失礼の恐れ」の応答を理由つきで差し戻す
SHAZAI_BACKENDjev（既定）／llm-s1
SHAZAI_LOG判定の記録を追記するJSONLのパス
SHAZAI_REPLAY保存した答えで動かす（試験用）

差し戻した後の応答（stop_hook_active）は差し戻さないので、差し戻しが繰り返されることはありません。判定できないときは何もしません。

組み込みで使うときの注意

  • 受け手モデルの数値は事前値で、人間のデータで推定していません。まず notify で記録をため（SHAZAI_LOG）、人の判断と突き合わせてから差し戻しを使ってください。
  • 毎ターン判定すると、謝罪の場面でない普通のターンも判定します。多くは「問題なし」になりますが、技術的な長い報告は「長さ」の失点を受けることがあります。
  • 送る内容は会話そのものです。外部のサービスに送ってよい会話かを、使う前に確かめてください。

6. 危険と対策

危険内容対策
字義通りの読み・間接性皮肉、慇懃な指摘、「二回伝えています」のような言外の依頼を取りこぼす具体的な型と例文を付けた一段の問いにする。皮肉・慇懃は独立した型にする。取りこぼしの率を検証で測る
日本語第三者評価は低資源言語での劣化を報告。日本語は未確認instructions を日本語版と英語版で用意して比べる。例文は日本語のまま
ルーブリック評定第三者評価で、ルーブリックに基づく評定は落ちるScore を減らし、数で定義できる欄は Noul の和にする。残る Score は段階ごとに例を付ける
Choice の順序先頭の選択肢に寄る並べ替えた2回の平均をとる。答えが分かれたら要確認にする
成果物の中の詫び下書きの中の詫びを、ユーザーへの詫びと数える前処理で切り出し、文ごとの問いは自分の発言の文だけに向ける
敵対的な内容評価対象の回答が、評価者への指示を含むstate はデータであり指示ではないと明記。疑わしい文は検出して記録する
版の移動jev-latest は新版で黙って動く版を固定し、版ごとに較正を作り直す
過剰な信頼「型の誤りが起きない」ことは「答えが正しい」ことではない欄ごとの一致度と較正を記録し、満たさない欄は LLM か代理観察に戻す
外部サービスへの送信会話と回答を TypeSafe に送る公開データだけを送る。人間の評定データや個人の会話は送らない

7. 検証の計画と採否の基準

  1. 段階1：欄ごとの一致192回答と作例の組について、jev・llm-s1・現行の observe・proxy の観察を作り、金ラベルとの一致を欄ごとに測る（真偽と Choice は κ、Score は重み付き κ、確率は Brier スコアと信頼性図）。
    基準：事実型の欄で κ ≥ 0.7、解釈型の欄で現行の LLM 観察との差が誤差の範囲内。満たさない欄だけ LLM に戻す（混成）。
  2. 段階2：層Bを通した一致それぞれの観察を simulate に通し、筆者の評定との κ、条件の順位、「失礼」の裾の割合を比べる。種を変えた10回で幅を出す。
    基準：筆者との κ が代理観察（0.28）を下回らない。条件の順位が保たれる。
  3. 段階3：人間のブラインド評定blind.py compare に各観察からのシミュレータの出力を並べる。比較のために、Jev に評定そのものを直接 Choice で問う方式（P1 を破る方式）も並べる。
    基準：人間の評定との所属度の近さが、現行の LLM 観察と同等以上。--obs-mode sample は、point より人間の分布に近いときだけ採用する。

Jev に評定を直接問う方式は、ほぼ費用ゼロで試せます。ペルソナ評定が失敗したのと同じ理由で失敗するのか、較正を目的に訓練されたモデルなら違うのかは、それ自体が知る価値のある問いです。

8. 発展：速さと確率が開くもの

観察が速く、安く、確率で返ってくると、費用の削減だけでなく、これまでできなかった使い方ができます。

一文の寄与を測る

一文ずつ取り除いた版や言い換えた版を観察して層Bに通し、「どの一文がこの謝罪を崩したか」を失点の差として示す。P4（一つの失敗で崩れうる）を説明可能な形で見せる方法。

観察の頑健さを測る

言い換えた問い、並べ替えた選択肢で何度も観察し、答えの揺れを欄ごとに測る。揺れの大きい欄は、問いが悪いか本当に多義的か。後者は「解釈型」の候補を実測で選ぶ手がかりになる。

実行時の謝罪の点検

謝罪を返す前に層A→層Bを通し、「失礼と感じる人の割合」が高い候補を差し戻す。生成する LLM（System 2）と点検する Jev（System 1）の組み合わせ。5.8節はこの方向の最初の実装。

察しの検出

距離の変化や不満の明示は、ユーザー発話のたびに安く計算できる。受け手の detect は人間の System 1 の働きそのもので、それを System 1 のモデルで測るのは偶然ではない。会話が冷えた瞬間を謝罪の合図にできる。

生成と評価の循環

謝罪の候補を多数生成し、分布で選ぶ、または差分を返して書き直させる。ただしシミュレータの穴を突く謝罪が生まれる危険があるので、人間の評定で定期的に確かめる。
